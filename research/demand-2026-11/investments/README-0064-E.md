# 0064-E — аудит доказательств IATI перед прогнозом авиаспроса

Основание: спецификация `0064-global-investment-demand-architecture.md`, этап аудита после 0064-D.

**Масштаб:** только `research/demand-2026-11/investments/`. Сайт, калькулятор, SQLite production и IATI Datastore не затрагиваются. Без ключей, сетевых запросов и новых зависимостей.

## Почему

240 нормализованных IATI-активностей — не 240 независимых инвестиционных объектов. Родительские / дочерние записи, программы без фиксированных физических площадок, финансовые операции разного экономического смысла и ошибочные даты нельзя превращать в будущий авиаспрос.

## Новый `quality_audit.py`

Читает `candidates.jsonl` и `relations.json` из `bulk_detail.py`. Создаёт:

- `summary.json` — объём и качество доказательств по издателям, финансовым типам и географии;
- `activities_review.csv` — построчная очередь для каждого IATI ID (исходные версии не удаляются);
- `locations_review.csv` — каждая исходная геозапись, её класс, точность и повторяемость;
- `future_related_groups.csv` — группы связанных записей со статусом `1` или `2` и плановой датой окончания в 2027–2036. **Группа не равна физическому проекту!**

Группировка использует только явные связи IATI `related-activity` type `1` (parent) и `2` (child). Названия и координаты не используются для автоматического объединения; другие типы связей не делают объекты одинаковыми. У двух отдельных кредиторов могут оставаться разные IATI ID для одного объекта — это вопрос ручной проверки.

Коды географии: `location-class=1` административная территория, `2` населённый пункт, `3` объект (Structure), `4` топографический объект; `location-reach=1` место активности, `2` место бенефициаров; `exactness=1` точное географическое обозначение, `2` приблизительное. Ни один код не устанавливает фактическое строительство / открытие. Даже `3 + 1 + 1` — *кандидат* на проверку, а не подтверждённая площадка.

**Не делаем:** суммы между commitment / disbursement / expenditure / budget / repayments / interest, пересчёт XDR/EUR/USD без указания даты и курса, присвоение точного аэропорта, «ввод» на основании future actual end, реконструкция истории доступности IATI из сегодняшнего снимка.

## Команда на сервере после деплоя

```bash
sudo systemd-run --wait --pipe --collect \
  --unit=fca-iati-quality-audit-0064e \
  -p User=agent \
  -p WorkingDirectory=/srv/fca/app \
  /bin/sh -c '
    base=/srv/fca/agent/research/iati/bulk
    src=$(find "$base" -mindepth 1 -maxdepth 1 -type d -name "structured-*" | sort | tail -n 1)
    test -n "$src" || exit 2
    test -s "$src/candidates.jsonl" || exit 3
    test -s "$src/relations.json" || exit 4
    out="$base/audit-$(date -u +%Y%m%dT%H%M%SZ)"
    exec /srv/fca/venv/bin/python /srv/fca/app/research/demand-2026-11/investments/quality_audit.py \
      --candidates "$src/candidates.jsonl" \
      --relations "$src/relations.json" \
      --out "$out" --as-of 2026-11-12
  '
```

Скрипт печатает счётчики, итоговые CSV/JSON остаются у `agent` в каталоге `0700` (файлы `0600`). Не создавать отдельный сервис/таймер: сначала нужно научиться идентифицировать физические инвестиционные события, а не только их финансовые записи.

## Очередь дальнейших исследований

1. Проверить реальные места, фактический статус и физические мощности аэропортовых/туристических/транспортных проектов. Не использовать координаты города/столицы как строительную площадку.
2. Установить cross-publisher связи (несколько кредиторов, один объект) с ручной проверкой, а не по совпадению строки названия.
3. Добавить архив исторических редакций: `snapshot_at` и `reported_last_updated_at` из текущей версии не доказывают `known_as_of` в прошлые годы.
4. Только после этого сформировать исторические event features для проверки baseline vs baseline+investments, без подмены O&D пассажиропотока.
